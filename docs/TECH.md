# Техническое задание

## 1. Архитектура

```
Телефон / браузер                                   Сервер (FastAPI)
─────────────────                                   ────────────────
видео ─► обрезка 2 с ─► MediaPipe Pose (в браузере)
                          │ координаты 33 точек × кадры (~0,3–0,5 МБ)
                          └──────────────────────────► сглаживание
                                                       фазы удара
                                                       пять показателей
                                                       DTW с эталоном
                                                       сохранение в БД
                                                          │ только числа
                                                          ▼
                                                  LLM (Ollama cloud): 2 предложения
                                                  проверка: в тексте нет чисел «из воздуха»
                          ◄───────────────────────  результат
скелет + призрак + HUD + совет
```

Почему так:
- **Поза считается в браузере.** Видео не покидает телефон (важно для детей), нет расходов на GPU-сервер, работает без интернета.
- **Математика на сервере в Python.** NumPy и SciPy легко тестировать, формулы лежат в одном месте и не зависят от версии браузера.
- **LLM получает цифры, а не видео.** Совет можно проверить: любое число в тексте должно быть во входных данных, иначе берём текст по шаблону.

## 4. Конвейер обработки

### 4.1 Видео в точки (браузер)

1. Пользователь загружает файл или снимает в приложении. Показываем рамку «весь игрок и мяч в кадре».
2. Просим обрезать окно 1,5–2 с вокруг удара (двойной ползунок). Это главная защита от долгой обработки.
3. Частота кадров: определяем по `requestVideoFrameCallback` (разность `mediaTime` у соседних кадров). Если число странное (слоумо с iPhone хранит временную карту), спрашиваем руками: 30 / 60 / 120 / 240.
4. Гоним кадры через PoseLandmarker в режиме VIDEO. Сохраняем `landmarks` (экранные координаты 0–1, видимость) и `worldLandmarks` (оценка в метрах относительно таза).
5. Если у 240 к/с кадров больше 400, берём каждый второй. Цель: до 20 секунд на клип на среднем телефоне.
6. Отправляем на сервер: `fps`, массив точек (4 знака после запятой, gzip), шар (если отмечен), стопа (`auto`).

Известные риски: слоумо-файлы с iPhone и Android имеют разные временные метки, поэтому проверяем `mediaTime` на тестовых клипах в день 1.

### 4.2 Подготовка сигнала (сервер)

- Выбрать бьющую ногу: у какой лодыжки выше максимум скорости в окне. Левшу зеркалим по оси X, чтобы использовать общий эталон.
- Нормализация: центр координат в середину таза, масштаб по длине туловища (середина плеч ↔ середина таза) для сравнения с эталоном. Для метров используем отдельный масштаб (4.5).
- Сглаживание Савицкого–Голея, окно около 40 мс (в кадрах зависит от fps), порядок 3. Производные берём из того же фильтра (`deriv=1`). Для живого оверлея в браузере используем One Euro Filter.
- Точки с видимостью < 0,5 заменяем линейной интерполяцией по времени и помечаем в ответе.

### 4.3 Фазы удара

Эвристики, пороги вынесены в конфиг и подбираются на своих клипах:

| Фаза | Как находим |
|---|---|
| Контакт `c` | Максимум скорости стопы бьющей ноги в окне. Если мяч отмечен, уточняем по минимуму расстояния «носок ↔ мяч» в ±5 кадрах от пика |
| Замах `b` | Последний максимум сгибания колена бьющей ноги перед `c` |
| Опорная нога `p` | Кадр перед `c`, где скорость опорной лодыжки падает ниже 15% от пика |
| Сопровождение `f` | Когда скорость стопы падает ниже 20% от пика после `c` |

Всегда есть ручной ползунок «кадр контакта». Если автоопределение сомневается (пик не выражен), показываем предупреждение.

## 5. Показатели и формулы

Угол в суставе B между точками A и C:

```
a = A − B,  c = C − B
θ = arccos( (a · c) / (|a| · |c|) )
```

Угловая скорость сегмента, φ — направление вектора (например колено → лодыжка):

```
φ(t) = atan2(Δy, Δx)  (с np.unwrap)
ω(t) = dφ/dt  из фильтра Савицкого–Голея, градусы в секунду
```

| № | Показатель | Как считаем | Почему важен |
|---|---|---|---|
| 1 | Угол колена в контакте | θ по точкам бедро–колено–лодыжка бьющей ноги в кадре `c` | Недоразогнутая или перегнутая нога = потеря мощности |
| 2 | Наклон корпуса | Угол вектора «середина таза → середина плеч» к вертикали в кадре `c` | Корпус сильно назад поднимает мяч, сильно вперёд прижимает |
| 3 | Постановка опорной ноги | Расстояние от опорной лодыжки до центра мяча вдоль линии удара, в сантиметрах | Слишком близко или далеко меняет траекторию |
| 4 | Скорость голени | Максимум ω_shank в окне `[b, c+2 кадра]` | Главный источник скорости удара |
| 5 | Кинетическая цепочка | Моменты пиков ω бедра, голени, стопы: `t_thigh ≤ t_shank ≤ t_foot` и лаги в мс | Если голень разгоняется раньше бедра, часть энергии теряется |

Масштаб (метры на пиксель), по приоритету:
1. По мячу: пользователь отмечает центр и край, диаметр 22 см (размер 5): `s = 0,22 / d_px`.
2. По росту игрока: вводит рост, меряем высоту скелета в стоячем кадре.
3. Если нет ни того ни другого, показываем только углы и скорости в градусах, без сантиметров.

Скорость стопы в контакте: `v = s · |p(c+1) − p(c−1)| / (2Δt)`. Оценку скорости мяча (≈ k · v, где k по литературе около 1,1–1,3, подтвердить) добавляем только после калибровки на своих ударах.

Отклонение каждого показателя: `z = (x − μ_ref) / σ_ref`. Эталон даёт μ и σ по 5–10 ударам, при малой выборке σ ограничиваем снизу минимальным значением, чтобы не раздуть z.

## 6. DTW и призрак

Признаки на каждом кадре окна `[p − 0,2 с, f]`: угол колена, угол бедра (плечо–таз–колено), наклон корпуса, ориентация голени. Нормализуем z-оценкой по эталону.

```
D(i,j) = d(i,j) + min( D(i−1,j), D(i,j−1), D(i−1,j−1) )
```

- Окно Сакое–Чибы шириной около 15% длины, чтобы не было нелепых выравниваний.
- Обе серии ресемплируем до ≤ 200 точек.
- Выход: нормированное расстояние `D/(N+M)`, путь выравнивания, среднее отклонение по фазам.
- **Оценка похожести 0–100:** `100 · exp(−D_norm / τ)`. τ подбираем так, чтобы эталон «сам с собой» давал ≈ 100, а разные игроки расходились по шкале (leave-one-out по эталонам). Это похожесть на выбранный эталон, а не «качество удара вообще», и так и подписываем.
- **Призрак:** по пути выравнивания каждому кадру игрока ставим кадр эталона, сдвигаем по тазу, масштабируем по длине туловища, при необходимости зеркалим, рисуем неоновым с прозрачностью 50%.

## 7. Совет от ИИ

- Вход: JSON с пятью показателями, диапазонами эталона, отклонениями `z`, возрастной группой. Видео и имя игрока не отправляем.
- Промпт: «Ты тренер по футболу. Напиши два предложения по-русски, до 45 слов: что главное не так и одно упражнение. Не ставь медицинских диагнозов. Используй только числа из входных данных».
- Проверка: регулярка вытаскивает числа из ответа, каждое должно быть во входе. Иначе берём шаблонную фразу по самому большому `|z|` (словарь «показатель → фраза → упражнение»).
- Если LLM недоступен, всё работает на шаблонах. В ответе поле `source: "llm" | "rules"`, чтобы в интерфейсе честно писать, откуда текст.

## 8. API

| Метод и путь | Что делает |
|---|---|
| `GET /api/health` | Статус, провайдер ИИ, число эталонов |
| `POST /api/attempts` | Принимает точки, fps, мяч; возвращает фазы, показатели, `z`, DTW, ряды для графиков |
| `GET /api/attempts/{id}` | Достаёт сохранённый результат |
| `POST /api/attempts/{id}/advice` | Строит совет (LLM или шаблон) |
| `GET /api/refs`, `POST /api/refs` | Список эталонов; тренер превращает попытку в эталон |
| `POST /api/players`, `GET /api/players/{id}/progress` | Игрок; ряды показателей и линия тренда (МНК: `β = Cov(t,y)/Var(t)`) |
| `POST /api/teams`, `POST /api/teams/{code}/join`, `GET /api/teams/{code}/summary` | Команда по коду/QR; сводка и самые частые отклонения |
| `GET /api/demo/seed` | Загружает демо-игроков и демо-попытки, везде помечено `is_demo` |
| `DELETE /api/players/{id}` | Удалить игрока и все его данные |

Размер запроса: 480 кадров × 33 точки × 4 числа ≈ 63 тысячи чисел, около 400 КБ в JSON, с gzip заметно меньше.

## 11. Тесты и проверка точности

1. **Синтетический скелет:** двухзвенная нога с известной функцией угла. Проверяем ошибку угла < 0,5°, скорость ω в пределах 2%, контакт ±1 кадр.
2. **DTW:** растянутая во времени копия кривой выравнивается; расстояние растёт при росте различий.
3. **Золотые клипы:** 3 реальных клипа с ожидаемыми показателями ± допуск.
4. **Валидация по Kinovea:** на 10 кадрах каждого из 5 клипов руками измеряем угол колена и наклон корпуса в Kinovea, считаем среднюю абсолютную ошибку и показываем число на слайде и на `/method`. До измерения никаких цифр точности никому не говорим.
5. **Скорость:** обработка клипа 2 с при 120 к/с ≤ 20 с на среднем телефоне.

## 12. Приватность

- Видео не загружается, только 33 точки скелета. Лица на сервере нет.
- Экран согласия при первом запуске; для детей нужно разрешение родителей (текст согласия готовим вместе с тренером).
- Кнопка «Удалить мои данные» убирает игрока и попытки.
- Хранится никнейм без фамилии, команда по коду.
- Никаких диагнозов, только «особенности техники». В тексте советов запрещены слова «травма», «вальгус», «риск».

## 13. Деплой

- Один Docker-образ: сборка фронтенда (Node) и бэкенд (Python), как в Aha.
- Файлы MediaPipe (wasm и `pose_landmarker_full.task`) копируем в `frontend/public`, чтобы приложение не зависело от внешних CDN.
- Переменные окружения: `OLLAMA_HOST`, `OLLAMA_API_KEY`, `LLM_MODEL`, `DATABASE_URL`, `ALLOWED_ORIGINS`.
- Бесплатный Render засыпает через 15 минут, при питче открыть сайт за 2 минуты до выхода.
- Для дублирования питча: статический демо-режим, который открывается без бэкенда.

## 14. Что не делаем сейчас

- Автодетекция мяча (P2).
- Анализ травмоопасности.
- Нативное мобильное приложение.
